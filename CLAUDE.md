# Working in this repo

## Deploy convention: push straight to `main`

Rusty is not a developer and works from his phone. He wants changes to go live without
having to review and merge a pull request.

**So: commit content and copy changes directly to `main` and push. Do not open a PR for them.**

Netlify is Git-connected to this repo. A push to `main` triggers a build (`python3 src/build.py`)
and publishes to https://blaisebaptist.netlify.app automatically, usually within a minute.
Nothing else is needed to deploy — no CLI, no manual upload.

Before pushing, always run `python3 src/build.py` locally and confirm it succeeds. A build
failure on Netlify means the site silently keeps serving the previous version, which is easy
to miss.

### When to use a PR anyway

Open a PR and ask first if the change is structural rather than content: reworking the build
script's page/nav model, changing `netlify.toml`, touching `netlify/functions/`, or anything
that could take the whole site down. Content, copy, new pages, and styling go straight to `main`.

### This changes when the real domain moves

Today `blaisebaptist.netlify.app` is a preview site. The congregation's actual website is still
the old Wix site at `blaisebaptist.org`, which this repo does not touch. That is why pushing
straight to `main` is low-risk right now.

**When `blaisebaptist.org` is pointed at this site, switch back to the PR-and-preview flow** so
changes get reviewed before the congregation sees them. Flag this to Rusty when that migration
comes up — he has asked to be reminded.

## Content notes

- Every page is generated by `src/build.py` into `dist/`. Never hand-edit `dist/` — it is
  gitignored and fully regenerated on each build.
- To add a page: write a function in `build.py`, register it in `PAGES`, and if it belongs in a
  dropdown, add it to the matching nav list (e.g. `MINISTRY_ITEMS`).
- See `README.md` for the brand system, Planning Center link conventions, and known gaps.
