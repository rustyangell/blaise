# Blaise Baptist Church — website

Static site for Blaise Baptist Church in Mocksville, NC. Plain HTML and CSS generated by one Python
script, deployed from this repo by Netlify. Day-to-day content — events, registrations, forms,
groups, the calendar — lives in Planning Center Church Center rather than being duplicated here.

This README is written for someone picking the repo up cold. It assumes no prior context.

## Start here

**This is not the live public site yet.**

## How `src/build.py` is organized

Read this before changing anything; it is most of what you need to know.

**`LINKS` dict, at the top.** Every external URL in one place — Church Center forms, the giving
platform, social, maps. Changing where a button points is a one-line edit here rather than a hunt
through the file. Worked example: `LINKS["childcare_registration"]` feeds all three childcare
enrollment buttons, so if that registration moves, one line changes.

**`PAGES` and `UNLISTED_PAGES`, at the bottom.** Each entry is
`(path, title, meta description, function)`. Adding a page means writing a function and adding one
tuple. `UNLISTED_PAGES` renders with `noindex, nofollow` and appears in no nav or footer —
reachable by direct URL only (currently just `classifieds.html`, the job openings page).

**Nav lists, near the top:** `NAV_ITEMS`, `ABOUT_ITEMS`, `MINISTRY_ITEMS`, `NAV_ITEMS_AFTER`.
Moving a page between the top level and a dropdown means moving one tuple between lists. Childcare
sits in `NAV_ITEMS_AFTER` rather than under Ministries because parents often come to the site for
it alone.

**Shared helpers — reuse these rather than writing new markup:**

- `modal_link()` / `plain_link()` — two different link behaviors. The distinction matters; see
  [Planning Center integration](#planning-center-integration--how-the-links-behave-and-why).
- `serve_callout(area)` — the "Want to serve with …?" block.
- `icon_badge()`, `directions_block()` — ministry icons and the map/address block.
- `nav(active)`, `render()` — the shared chrome.

**One page function returns one page's HTML** as an f-string. `render()` wraps it in
`PAGE_TEMPLATE` with the shared nav and footer. That is why editing `nav()` updates all 14 pages
at once, and why there is no per-page HTML file to keep in sync.

## Making a change, end to end

```bash
git checkout -b some-descriptive-branch
# edit src/build.py or src/styles.css
python3 src/build.py                    # writes dist/, prints "Built 14 pages into ..."
python3 -m http.server -d dist 8000     # then open http://localhost:8000
```

Then commit, push, and open a pull request. Netlify builds a **deploy preview** at its own URL and
posts the link on the PR. Look at the preview. Merging the PR into `main` deploys to production
automatically — Netlify runs `python3 src/build.py` and publishes `dist/`.

Build settings come from `netlify.toml` in this repo, so there is nothing to configure in the
Netlify dashboard.

Manual deploy from a laptop, if ever needed:

```bash
python3 src/build.py
netlify deploy --prod --site 64f6e724-fa41-4cc5-bbf1-df1232a4876d --dir=dist --functions=netlify/functions
```

## Before you push

A change can build cleanly and still be wrong. This checklist is where that gets caught.

- [ ] **Build it.** `python3 src/build.py` should print `Built 14 pages into …`.
- [ ] **Actually look at the page.** Read the rendered result, not just the diff. A hero button
      once shipped invisible because it was dark-on-dark; the diff looked perfect. With no browser
      to hand, render it headless:
      ```bash
      /opt/pw-browsers/chromium-*/chrome-linux/chrome --headless --no-sandbox \
        --window-size=1280,900 --screenshot=out.png "file://$PWD/dist/childcare.html"
      ```
- [ ] **Grep `dist/` to prove it landed.** Especially for renames — the old term should return
      nothing: `grep -ri "old name" dist/`. A half-finished rename is the classic failure.
- [ ] **Check a narrow viewport.** The nav collapses into a drawer below 860px.
- [ ] **Never edit `dist/`.** Fix the source and rebuild.

## Gotchas

Each of these has bitten someone. The reason is included so it doesn't get re-introduced.

- **`dist/` is generated and gitignored.** Anything edited there disappears on the next build.
- **Registrations must not use the Church Center modal.** It hangs on an infinite spinner. See the
  Planning Center section below for the full reasoning.
- **Buttons inside `.page-hero` sit on a dark forest gradient.** The default `.btn-primary` and
  `.btn-outline` are styled for light backgrounds — the outline variant is forest-on-forest and
  invisible until hover swaps the colors. `.page-hero` overrides both in `styles.css`. If you add a
  hero button, render the page and confirm; don't assume.
- **Childcare is a business that employs staff, not a volunteer ministry.** The "Interested in
  Serving" callout does not belong on that page — volunteering is the wrong ask. Job openings have
  their own home at `classifieds.html`.
- **Content that changes often belongs in Church Center, not this repo.** This boundary is
  deliberate: it is what lets staff manage events, registrations, and forms themselves without
  touching code. Apply it to every new request. If something will need editing monthly, the right
  answer is usually a Church Center object the site links to, not new markup here.

## Planning Center integration — how the links behave, and why

All form/event/group links point to `blaisebaptist.churchcenter.com` (URLs collected in the `LINKS`
dict at the top of `src/build.py`). Two different link behaviors, deliberately:

- **People Forms** (Connection Form, Baptism Interest, Parent/Child Dedication, Interested in
  Serving, Missions Interest) use Planning Center's official popup embed: a
  `<script src="https://js.churchcenter.com/modal/v1">` tag plus
  `data-open-in-church-center-modal="true"` on the link (see `modal_link()`). These open as a modal
  right over the page. Confirmed working live.
- **Registrations/reservations** use `plain_link()` — a normal link that opens in a new tab.
  **Do not put these in the modal** — tried it, and the modal hangs on an infinite spinner and never
  loads. Best-grounded guess: those pages can involve payment, and payment pages commonly refuse to
  be framed for clickjacking-security reasons. Not documented explicitly by Planning Center, but
  reproducible. These links also point to the event's public **info page**
  (`/registrations/events/{id}`), not straight to `/reservations/new` — the info page loads with no
  sign-in required and lets people read details before registering.

## Live events from the Planning Center API

`netlify/functions/events.mjs` serves `/api/events`: upcoming (90 days) Calendar events marked
*Visible in Church Center*, plus every open, unarchived Registrations signup. It authenticates with
a Personal Access Token stored as Netlify env vars `PCO_APP_ID` / `PCO_SECRET` (secret; set in the
Netlify UI, never in the repo). The CDN caches the response for 15 minutes and serves the last good
copy for a day if Planning Center is down.

`src/assets/events.js` fills any `data-pco="signups" | "events" | "home"` container on the events
and home pages. Those containers ship with a Church Center link as fallback content. Calendar events
whose registration URL matches an open signup are shown once, as the signup. To hide an event from
the site, set it to Hidden in Church Center; there is nothing to edit here.

## Brand system

Source: `Brand Guide One-Pager.pdf` in the client's branding folder. Tokens are duplicated as CSS
custom properties at the top of `src/styles.css`:

- Forest Green `#1A3A1A` (headlines), Sage `#8CA08C` (support only), Off White `#F5F5F0`
  (background), Near Black `#1A1A1A` (body text)
- Ministry colors: Kids Teal `#00A878`, Youth Orange `#F08C00`, Men Navy `#142864`,
  Women Mauve `#6B3D52`
- Font: Josefin Sans (Google Fonts) — Bold headings, Regular body, Light fine print only
- Voice: warm, plainspoken, specific (name Mocksville/Davie County) — not marketing copy
- Real logo/ministry-icon PNGs live in `src/assets/`, copied from the brand kit. Note: the brand kit
  has no true light-colored logo file, so `.logo-inverse` uses a CSS filter to flatten the green
  mark to white for dark backgrounds (see comment in `styles.css`). Ministry icon art is tinted
  close to its own ministry color, so icons sit on a white `.icon-badge` for contrast rather than
  being recolored.

## Going live — DNS cutover runbook

Not done yet. This is the step that makes `blaisebaptist.org` serve this site instead of Wix.

### What's true today

- **DreamHost** is both the registrar and the authoritative DNS host for `blaisebaptist.org`.
- Apex A records point at **Wix** (`185.230.63.x`).
- `www` resolves to Cloudflare IPs. This is almost certainly Wix's own CDN fronting their
  hosting, not a Cloudflare account the church controls — confirm in the DreamHost panel rather
  than planning around it as an obstacle.
- **All MX records point to Google Workspace.** Staff email (`@blaisebaptist.org`) depends on them.

### The one rule

> **Change only the apex A record and the `www` record, both in DreamHost. Do not change
> nameservers, and do not touch any MX or TXT record.**

Google Workspace needs the MX records plus the SPF, DKIM (`google._domainkey`), and DMARC
(`_dmarc`) TXT records. Editing A records leaves all of that alone. Switching DNS hosting to
Netlify to "tidy things up" does not — it silently drops every record you don't recreate, and
church email goes dark. That is the most likely way this goes wrong.

### Steps

1. **Screenshot the full DreamHost record set first.** That is the rollback.
2. **Lower the TTL** on the apex A and `www` records to 300s, a day ahead. Makes a bad cutover
   reversible in minutes rather than hours.
3. **Decide the canonical hostname.** Recommended: apex (`blaisebaptist.org`) with `www`
   redirecting to it — shorter to say out loud.
4. **Add the custom domain in Netlify** to the `blaisebaptist` project. It will display the exact
   records to create. Use its values.
5. **In DreamHost, repoint the apex A and `www` records** to what Netlify gave you. Nothing else.
6. **Verify:** the site loads on both apex and `www`; TLS is valid (Netlify auto-provisions
   Let's Encrypt once DNS resolves); and — separately — send *and* receive on a
   `@blaisebaptist.org` address, checking that outbound mail isn't flagged as spam. That last check
   is what proves SPF and DKIM survived.
7. **Leave Wix running** for a couple of weeks before cancelling, in case something surfaces.

### Before the cutover

Old Wix URLs are indexed and bookmarked, and will 404 the moment the domain moves. Audit them and
add redirects to `netlify.toml` first. The `/childcare` redirect already there is the pattern:

```toml
[[redirects]]
  from = "/childcare"
  to = "/childcare.html"
  status = 301
```

## Campus map (About page)

- `src/buildings.json` is the single source of truth for buildings (`id`, `number`, `name`, `description`
  for the click panel, `hover` for the short hover popup).
- `src/campus-map.svg` holds one shape per building (`data-building` = building id). Footprints were traced
  from Google map/satellite screenshots in `reference/campus/` (not in the repo) and rotated to match the
  church's own campus map. Only our own flat vector ships; no Google imagery goes into `dist/`.
  `build.py` inlines it and makes each shape a focusable button with an aria-label.
- `src/underground-inset.svg` is the Youth Underground floor plan. It pops up only while the Underground
  entrance marker is hovered/focused, or while Youth Underground is selected.
- `MINISTRY_LOCATIONS` in `build.py` says which building each ministry meets in. The map panel's ministry
  list and each page's "Find it on the map" link (`find_on_map(page)`) both come from it. A page's
  first row is its primary building. The build fails on an unknown building id.
- Deep link: `/about?building=<id>#campus-map` selects that building and opens its panel
  (`src/assets/campus-map.js`). On phones the panel is a bottom sheet.
